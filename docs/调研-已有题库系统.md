## 二、三条参照的核心做法

### ① MathCyclus（开源，最接近）

- 题库管理：**按「板块 / 年份」自动归档**；`problem` / `answer` / `solutions` 环境分离题干、答案、解析；
  元数据记录 **ID、标签、难度、来源、备注、引用次数**
- AI 辅助录入：截图 → 规范 LaTeX；**自动生成知识点标签与难度星级**；
  **「教学审核」** —— AI 识别解答时自动审核逻辑，发现错误则标注原错并附 AI 纠错
- 智能组卷：支持**题型 / 年份 / 板块 / 标签 / 难度 / 全文检索**；
  **按知识板块、题量与目标难度分布进行抽样**；可选语义搜索（本地 SQLite 向量索引，可重建）
- 工作台：**三栏布局（左筛选 / 中编辑 / 右预览与 AI 助手）**；徽章式展示星级、标签、备注
- 去重：**批量录入遇到已存在的同名题，保留旧文件并跳过，日志明确标记为「跳过」**
- 本地统计：`local_stats.sqlite3` 记录本机新增、修改、活跃度

### ② 菁优网（商用组卷）

- **双向细目表组卷**：教师设置一份细目表（**知识点、难度、来源、题型**），系统一键挑题，也可手动挑选
- 流程：**基础信息填写 → 知识点挑题 → 分值设置 → 组卷预览 → 排版下载**

### ③ 考试云（通用题库）

- 导题：**Word / Excel / Txt / AI** 多模板
- 分类：**支持无限层级知识分类创建**
- 难易度：按**难度系数随机出题**
- **重复试题检查：导入或组卷时自动检查，避免试卷中出现相同试题**
- 组卷方式：**固定 / 随机 / 抽题 / 混合**
- 试题更新 · 试题分析

## 四、我们已经做对、且与他们一致的

- 题目结构分离：`stem` / `answer` / `solution` ＝ 他们的 problem / answer / solutions
- 元数据：ID / 标签 / 难度 / 来源 —— 我们都有，还多了**题型 / 板块 / 日期**
- 按板块与年份归档；六大板块 + 日期字段
- **导入去重：跳过并回报条数** —— 与他们的「跳过并标记」一致
- 难度分级（易/中/难）≈ 他们的难度星级
- **公式：他们用 LaTeX 编译预览（需 TeX Live）；我们用 MathJax，无需外部依赖，更轻**

## 五、不建议照搬

- 错题本 / 刷题模式 / 答题统计 / 多终端 —— **学生侧功能**，我们是教师备课工具
- AI 截图转 LaTeX / 语义搜索 —— 需要 AI 通道或重依赖，列为待办，暂不做
- TikZ + xelatex 几何图预览 —— 要装整个 TeX Live；我们用 MathJax 更轻

## 六、他们点到的痛点，正是我们的短板

> 「传统方式难检查重复试题，经常在试卷中出现相同试题」

我们现在**只在导入时按题干去重**，**组卷时没有查重** —— 手动勾选很容易选到两道相同或高度相似的题。

## 七、建议的改造顺序（按性价比）

1. **规则/细目表组卷** ⭐⭐⭐ —— 设「题型 + 板块 + 难度 + 数量」→ 一键挑题进试卷；
   同时做**组卷查重**（同一份卷子内题干重复/高度相似的提醒）
2. **分值设置** ⭐⭐ —— 每题分值、卷面总分；试卷头部显示总分与题量
3. **知识点层级** ⭐⭐ —— 板块之下加第二级（章节），支持逐级筛选（先不加第三级）
4. **题目备注 + 引用次数显示** ⭐ —— 元数据加 `note`；列表/详情显示 `usedCount`
5. （可选）本地活跃度统计

## 八、按调研结论做的改造（第一期：规则组卷 + 查重）

**借鉴来源**：菁优网「双向细目表组卷」+ 考试云「组卷时自动查重」。

| 项 | 实现 |
|---|---|
| 规则 | `PaperRule { qtype, section, level, count }`，可加多条（细目表一行一条）|
| 抽题 | `pickByRules()`：**同一道题只抽一次**（后面的规则自动跳过已选）；默认**优先抽用得少的**，可切随机；**题量不够如实回报 short**，不凑数不重复 |
| 查重 | `findDuplicates()` 两层：**归一化后完全相同** + **字符二元组 Jaccard ≥ 0.85** 的近重复；界面显示相似度与两题标题 |
| 范围 | 从**当前筛选结果**里抽，可先按题型/板块/难度/标签缩小范围再抽 |
| 送卷 | 按 选择→填空→解答 排序后送进 PDF 生成 |

**实测结果（干净状态，先灌 6 道：3 单选 + 2 填空 + 1 解答，含一对重复录入的题）**：

- 默认规则「单选 × 5」→ **命中 3 / 5，并明确显示「库里只有这么多，少了 2 道」**
- 查重 → **发现 1 组疑似重复：完全相同 #361 集合交集 ↔ #362 集合交集(重复)**
- 单元测试（Node 直接跑纯函数）：抽题条数与 short 正确、**同题绝不重复抽**、归一化相同能查出

**已知限制（界面已写明）**：近重复只认「文字高度接近」的（错字、空格、标点）；
**语义相同的改写认不出来**，需要人工核对 —— 那需要 AI，列为待办。

## 九、一个重要教训：陈旧 UI 状态会让验证误判

验证过程中曾出现「`lib_query` 返回 0 条，而界面上列了 214 项」，一度被定性为**数据源错误**。

**实际原因**：题库弹窗**只在打开那一刻加载一次列表**，之后不自动刷新。
那个弹窗是在「库里有 214 道」时打开的，随后库被清空，**DOM 里还留着旧列表**。

**教训**：

1. **每次端到端验证都要在干净状态下跑** —— 先清空库、再灌已知数据、再打开界面；
2. **看到「界面与库不一致」时，先怀疑验证方法**（陈旧状态、连错进程），**再怀疑产品**；
3. 顺手加了一个**「刷新」按钮**（列表只在打开时加载一次是合理设计，但要有手动刷新手段）。

## 十、结论


我们的题库存取层与元数据设计**方向是对的**（与他们一致），主要差距在
**「组卷的智能化」**与**「分类的深度」**上 —— 优先补 1、2 两项即可明显提升可用性。
