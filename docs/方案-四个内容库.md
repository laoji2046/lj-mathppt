# 方案 · 四个本地内容库（公式 / 数学图形 / 试题 / 课件）

> 用户选定动机 **C：题库 / 素材的结构化检索**
> 需求原话：「想要一个公式库、一个数学图形库、一个 PDF 生成用的数学试题库、一个课件库」
> 结论：**走 ① SQLite 本地库** ✓ 不必上远程 ✓

## 一、为什么是 SQLite（而不是继续 localStorage 或上远程）

- **要检索** → SQLite 内建 **FTS5 全文索引**；中文需配分词方案（见风险 3）
- **要结构化** → 试题有 题干/答案/解析/知识点/难度/来源，天然是表
- **要长期增长** → localStorage 5~10 MB 天花板（已知试卷草稿就 230 KB）
- **不上远程** → 保持离线单机身份，无账号，无冲突

## 三、表结构（草案）

### 通用主表（四个库共用，用 type 区分）

    library_item(
      id INTEGER PRIMARY KEY,
      type TEXT NOT NULL,          -- formula | figure | question | deck
      title TEXT NOT NULL,
      body TEXT,                   -- 公式 LaTeX / 图形配置 JSON / 题干 / deck JSON
      meta TEXT,                   -- JSON：其余结构化字段
      tags TEXT,                   -- 逗号分隔（另有 tag 表）
      source TEXT,                 -- 教材 / 导学案 / 自编
      builtin INTEGER DEFAULT 0,   -- 来自静态库的条目
      created_at TEXT, updated_at TEXT,
      used_count INTEGER DEFAULT 0
    )
    tag(id, name, kind)
    item_tag(item_id, tag_id)

### 各库专有字段（存 meta JSON，避免表爆炸）

    formula  : { latex, kind, note }
    figure   : { figKind, params, size, style }    -- 复用 mathPlot 的 kind/params
    question : { stem, options, answer, solution, knowledge, difficulty, year, region }
    deck     : { slideCount, width, height, theme }

### 全文检索（第二期再启用）

    library_fts USING fts5(title, body, tags, content=library_item, content_rowid=id)

## 五、迁移（最容易出事的一步）

首次启动：

1. 检测数据库文件是否存在，不存在则建表
2. **把 localStorage 现有数据导入**：formula-presets → formula 表；deck → deck 表
3. **把静态库灌进去作为内置条目**：formulaLibrary.ts → formula 表（builtin=1）
4. 记录迁移标记，避免重复导入
5. **保留回滚路径**：库文件独立存放，原 localStorage 至少保留一个版本周期不删

⚠ **不做第 2 步 = 用户打开发现自己的公式预设全没了**，这是本项目最怕的事故类型。

## 六、分期（建议顺序）

    **第一期：公式库** ← 最小闭环
      · 已有静态数据可灌（formulaLibrary.ts）
      · 已有用户数据要迁（formula-presets）
      · 入口单一（FormulaInserter）
      · 能立刻验证「迁移 + 检索」两条最关键的链路

    **第二期：试题库** ← 价值最大
      · 结构化字段最多（题干/选项/答案/解析/知识点/难度）
      · 直接服务 PDF 生成的组卷
      · 需要设计录入界面（较费工）

    **第三期：课件库 + 数学图形库**
      · 课件库 = deck 入库 + 列表/搜索/打开
      · 图形库 = mathPlot 的 kind/params 存库

## 七、风险与验证

1. **体积**：rusqlite 约 +1~2 MB。刚把 exe 从 39.92 压到 29.08 MB。
   → 交付前复测 exe 体积与启动时间。

2. **迁移丢数据** ⚠⚠ 见第五节。必须先备份 localStorage 再导，并保留回滚。

3. **中文全文检索**：FTS5 默认分词器对中文按字切分，效果一般。
   → 第一期先用 LIKE + 标签过滤（够用），FTS5 留到第二期评估。

4. **数据库文件放哪**：exe 同目录还是用户目录，要定。
   → 建议放用户目录下的固定位置，与 exe 解耦（换 exe 不丢库）。

## 十、第二期补充：试题批量导入（已完成）

**为什么做**：一道一道录太慢；老师手里的题通常已经是文档。

**落地内容**：

| 项 | 实现 |
|---|---|
| Rust | 新增 `lib_save_many`（事务批量写入 + 按 type+body 去重） |
| 解析器 | `src/composables/parseQuestions.ts`（纯函数，独立可测） |
| 数据层 | `importParsedQuestions()` |
| 界面 | 题库弹窗加「批量导入」面板（粘贴区 + 实时识别数 + 格式说明 + 前 5 道预览） |

**解析规则**：

   题目分隔  一行 --- 分隔；或每道题以 1. 2. 3. 开头（自动识别）
   选项      行首 A-H（可带括号/顿号/点）；同一行多个选项也能拆
   答案      【答案】D 或 答案：D
   解析      【解析】…（可多行，直到下一个标记）
   知识点    【知识点】a, b 或题干里的 #标签
   难度      【难度】1-5
   来源      【来源】…（顺带识别其中的年份）

**实测结果（在 exe 里走完整 UI 路径）**：

- 粘贴 293 字符样例 → 界面实时显示「识别到 3 道题」
- 点「识别并导入」→ 题库 **3 条**，字段全部正确：
  选项数 / 答案 / 难度 / 知识点（含 `#和定积最大` 被正确剥离 # ）/ 来源
- **去重**：连续导入同一条 3 次 → `added:1` 然后 `added:0, skipped:1` 两次 → 库里只有 **1 条**
- 测试数据已清理，题库回到 0 条

**解析器单独验证**：用 esbuild 编成 CJS 后用 Node 跑样例（不依赖界面）——
发现并修掉一个 bug：知识点行里的 `#标签` 没被剥离 `#`（`splitTags` 未把 `#` 当分隔符）。

**体积回归**：exe 30.68 MB → **30.71 MB（+0.03 MB）**。
