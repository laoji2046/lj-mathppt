## 11:30 关键修复（版本 2026.09.1109）

- **「拖动放大后混排内容被截断」的真凶：`transform-origin` 与 flex 对齐不一致。**
  混排宿主是 `justify-content: flex-start`（align=left 时），内容贴左边缘；
  而缩放写的是 `transform-origin: center center` → 放大后有一半跑到左边框外，被 `overflow: hidden` 裁掉。
  现象特征：**左边被切、右边完好** —— 我当时没细看方向，误判成测量问题，白改两轮。
  修法：原点跟随对齐 —— `transformOrigin = (align === 'left' ? 'left' : align === 'right' ? 'right' : 'center') + ' center'`；
  导出侧给 `.fx-mixed` 写 `data-align`，`fitMixed` 读它取原点，保证 PDF/PNG/放映与画布一致。
- **教训：先看裁切方向**。左右被裁 → 对齐/缩放原点问题；上下被裁 → 高度测量/换行问题。
- 保留的加固（针对 MathJax 溢出父盒却不撑大父盒）：真实占位 `max(offset, scroll)`、按绘制范围并集兜底、
  渲染后 rAF + 120/420ms 复量、`ResizeObserver` 同时盯内容节点。
- `fitMode`（fill/shrink）与 `autoBox`（插入时外框贴合内容）是自由缩放的基础：**空有大框 + fill 就是 1101 "公式过大"的成因**。
- 构建坑：`dist/assets` 会堆历史产物（曾 157 个 / 87 MB，Tauri 把整个 dist 打进 exe → 58 MB），
  已加 `clean-dist.cjs` 并在 README 构建步骤注明；exe 降到 30 MB。

### 坑（血泪）：不要用 PowerShell 改含中文的源码文件
- `Get-Content -Raw` + `Set-Content -Encoding UTF8`（Windows PowerShell 5.1）会**按 GBK 解码 UTF-8 文件**再写回 → 整个文件中文变乱码、
  更糟的是 GBK 双字节会把后面的 ASCII 引号**吞掉**，导致字符串未闭合（本次直接损坏 pptLayouts.ts，17 处）。
- 抢救办法（已成功）：按 `[Text.Encoding]::GetEncoding('GBK').GetBytes(乱码文本)` 还原原始 UTF-8 字节再 `UTF8.GetString` 解码回来；
  但被替换成 `?` 的少数字符不可逆 —— 之后按行扫描「引号不成对 / 含 U+FFFD」逐处补齐即可。
- **正确做法**：一律用 edit / write 工具改文件；需要批量替换时写 node 脚本（`fs.readFileSync(p, 'utf8')` / `writeFileSync(p, s, 'utf8')`）。
